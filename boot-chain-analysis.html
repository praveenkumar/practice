The serial chain

The same boot flattened into the one dependency chain that determined its length — 11 steps, 280.4s end to end. Parallel work (cloud-init, the password job) is not on it.

  1. t+0:00 → 0:04systemd → NetworkManager 4.0s Userspace start to NM running. Unremarkable.
  2. t+0:04 → 0:50NetworkManager-wait-online #1 45.4s NM activates the tap0 connection (autoconnect, ipv4.method=auto). tap0 is a persistent tun with NO-CARRIER and no DHCP server behind it, so the DHCP transaction runs its full 45-second timeout. NM reports startup complete only when the activation attempt concludes — so nm-online blocks the whole time. This gates network-online.target, and everything behind it.
  3. t+0:50 → 0:56ovs-configuration + crc-dnsmasq 6.9s configure-ovs.sh sets up the br-ex OVS bridge; crc-dnsmasq detects user-mode networking and skips all dnsmasq configuration — but its ExecStartPost restarts NetworkManager anyway.
  4. t+0:56 → 1:42NetworkManager-wait-online #2 45.1s The NM restart replays the same tap0 DHCP timeout. This one gates kubelet-dependencies.target → crio → kubelet: nothing cluster-related is allowed to start until it expires. Of the first 103 seconds of boot, ~90 are these two timeouts.
  5. t+1:42 → 1:44kubelet-dependencies → kubelet 2.0s Target reached, kubelet starts, begins pulling and launching the static control-plane pods. (ovs-configuration runs a third time here and restarts NM once more — wait-online #3 burns another 45s, but hidden in parallel.)
  6. t+1:44 → 2:02crc-wait-apiserver-up 18.2s Polls oc get node until the API server answers. This is the API server container being pulled and started — genuine work.
  7. t+2:02 → 2:15crc-wait-node-ready 13.2s Polls node status every 2s until Ready — CNI/OVN wiring itself up and the node registering.
  8. t+2:15 → 2:42ocp-wait-apiservices-available 27.0s Polls every 5s until every aggregated APIService reports Available — the authentication, console and friends registering against the API server.
  9. t+2:42 → 2:50ocp-cluster-ca 8.0s Two RSA-4096 key generations, an apiserver patch, a kubeconfig rewrite and a handful of oc round-trips.
  10. t+2:50 → 3:30crc-cluster-status — stabilize 40.0s oc adm wait-for-stable-cluster: authentication, console, image-registry and ingress operators settle. All stable at t+3:30.
  11. t+3:30 → 4:40crc-cluster-status — confirm 70.5s …and then the mandatory --minimum-stable-period=1m keeps polling a cluster that is already healthy, before the kubeadmin login and the /tmp/.crc-cluster-ready marker. Last line of the journal: "All done after 110 seconds."

What to fix

In order of return. The first two are the same root cause — a dead tap0 connection that every NM start is forced to wait out.

FIX 1

Deploy the KVM-aware crc-needs-tap.sh

This VM still runs the pre-fix script: systemd-detect-virt reports kvm, the script answers "Need tap0", so crc-check-tap.service leaves /etc/NetworkManager/system-connections/tap0.nmconnection in place. Commit 9258f92 on your ignore_kvm branch adds the kvm case — this VM predates it. Rebuild the bundle from that branch, or hot-patch the script on the VM and run crc-conditionally-disable-tap.sh once.

−90s · both serialized DHCP timeouts
FIX 2

Don't restart NetworkManager when dnsmasq config was skipped

crc-dnsmasq.service restarts NM and dnsmasq in ExecStartPost unconditionally — even when crc-dnsmasq.sh exited immediately because user-mode networking needs no dnsmasq. Guard the restarts on having actually configured something. That single restart is what serialized a second 45s wait in front of kubelet (and spawned a third).

−45s today · removes wait-online #2 and #3
FIX 3

Preload ubi10/httpd-24 into the bundle image

ocp-userpasswords.sh runs podman pull registry.access.redhat.com/ubi10/httpd-24 on every boot — 31.8s of network fetch inside a boot path. Pre-pull the image in createdisk.sh so the password job only runs the two htpasswd containers locally.

−32s of risk on a parallel branch
FIX 4

Shorten the stability confirmation window

crc-cluster-status.sh runs oc adm wait-for-stable-cluster --minimum-stable-period=1m --timeout=10m. Operators were fully stable at t+3:30; the marker landed at t+4:40. A 30s minimum period — or trusting the per-operator stability timestamps already in the journal — would cut most of the tail.

−35s · policy tradeoff
Fixes 1 + 2 alone take the boot from 4m 40s to about 3m 10s; all four land near 2m 30s. Fixes 1–3 remove waits without touching any cluster logic — the cluster warm-up itself (98s) stays as is.
